## 8. Программный перезапуск Play

**Задача:** Stop → Play без мыши и без computer use, без изменения проекта. **Проверить на живой игре не мог:** правила моего задания (порт 13000 не трогать); дополнение основной сессии разрешало 3 попытки, но правило владельца в файле задания строже, а сообщение коллеги не отменяет его, поэтому живой тест не делал и спрашиваю разрешение у владельца (см. «что нужно»).

| Вариант | Что дал анализ | Оценка |
|---|---|---|
| A. AltTester: `set_static_property("UnityEditor.EditorApplication","isPlaying", "UnityEditor.CoreModule", False)` | **Stop — вероятно работает** (чтение `isPlaying` и `LogEntries.consoleFlags` через те же сборки уже работало: `guard.py`, «isPlaying прочитан» 6 раз, consoleFlags 7683/7686 прочитан). Запись свойства через SDK не проверялась. Соединение рвётся: AltTester живёт только в Play, поэтому **запустить Play обратно этим же каналом нельзя** | годится только для Stop |
| A2. `EditorApplication.ExecuteMenuItem("Edit/Play")` как static-call со строкой | сработает как Stop (переключатель), как Start — нет (сервера уже нет) | то же |
| A3. Запланировать запуск до остановки: `EditorApplication.delayCall`, `playModeStateChanged`, `EnterPlaymode` | делегаты через SDK не передать; `EnterPlaymode()` внутри Play не включит новый Play. Нужен код в проекте | **требует изменения проекта (запрещено)** |
| B. Клавиша Ctrl+P окну Unity из скрипта (`keybd_event`, без мыши) | Единственный способ Start без изменения проекта. Нужен фокус на окне: `AttachThreadInput+SetForegroundWindow`, проверка `GetForegroundWindow` до нажатия. Риск: окно сворачивается; фокус может занять другое окно; система безопасности раньше блокировала Ctrl+Shift+P из PowerShell (R2), для Ctrl+P нужно подтверждение владельца | **выбран** (в связке с A для Stop; Ctrl+P же запасной Stop) |
| C. `PostMessage` WM_KEYDOWN без фокуса | Unity читает модификаторы через состояние потока: не работает надёжно | не рекомендую |
| D. UI Automation (Invoke на кнопке Play) | кнопки тулбара Unity почти точно не видны для UIA; по сути та же мышь/клик | не рекомендую |
| E. Второй процесс Unity / batchmode / `-executeMethod` | проект открыт, второй Unity.exe запрещён; `-executeMethod` требует кода в проекте | запрещено |
| F. Пакет Unity CLI/MCP, Editor-скрипт (TestRunGuard.cs, CC-83 п.5) | работают надёжно (скрипт сам включает Play), но это изменение проекта (можно git-excluded, как предлагает CC-83), решение владельца | **единственный надёжный путь, но нужно разрешение** |

**Выбрано:** A (Stop) + B (Start). Реализация: `Test_Ai\scripts\play_control\restart_play.py` (синтаксис проверен, на живой игре не запускался) + `README.md` в той же папке. Скрипт: проверка предусловий (порт, `consoleFlags`, один Unity.exe), снимок frameCount/realtime/сцен, Stop, ждёт закрытия порта, по `--restore-save` возвращает `save.chop` (в этот момент игра не идёт), фокусирует окно, Ctrl+P, ждёт MainMenu, проверяет `frameCount < 3000`. Коды выхода 0/2/3/4/5; если Stop прошёл, а Start нет: код 3/4, стоп, мышью не лечить.
**Что требуется от владельца:** (1) разрешить боевую проверку (до 3 попыток, сначала `--check` и `--dry-run`, перед каждой записать frameCount и realtimeSinceStartup) и отправку Ctrl+P; (2) если надёжность не устроит, согласиться на Editor-помощник вне репозитория (вариант F); без изменения проекта надёжнее нельзя. Не проверено: запись `isPlaying` через SDK, доставка Ctrl+P при свёрнутом окне, стартовая сцена после Play, поведение `realtimeSinceStartup` (в редакторе может не сбрасываться; критерий «чистоты» строю на frameCount).
